# Три цикла независимого ревью

Приложение проверялось не только самопроверкой разработки. Между версиями проводилось внешнее
ревью: **отдельная сессия Claude Opus 5 без контекста разработки**. Ревьюер получал только код,
запускал его сам, писал собственные проверки и не знал, какие решения принимались и почему.

Роль задавалась отдельным промптом со строгими правилами. Ключевые из них:

> Оценивай результат, а не намерения автора. Не засчитывай как реализованную функцию: текст в
> README, комментарий в коде, красивый UI без работающей логики, обещание автора. Если что-то
> невозможно проверить — прямо укажи «не удалось проверить». Не награждай за сложность.
> Спрашивай не «можно ли представить, что это работает», а «доказано ли, что это работает».

Ниже — сокращённые рецензии. Полные оценки по девяти категориям, пошаговый разбор сценария и
доказательства по каждой находке остались в исходных рецензиях; здесь только суть.

## Ревью № 1 — первая версия

**Итог: 4.25 / 5 · вердикт «принять после исправлений»**

| Категория | Оценка |
| --- | ---: |
| Core task completion | 5 / 5 |
| Product correctness | 4 / 5 |
| Explainability | 4 / 5 |
| UX / usability | 4 / 5 |
| Edge cases / robustness | 4 / 5 |
| Scope / product judgment | 5 / 5 |
| AI / human control | 3 / 5 |
| Technical confidence | 5 / 5 |
| Documentation / verification | 4 / 5 |

**Как проверялось.** Прочитан весь код (4 557 строк), прогнаны typecheck / lint / test / build,
приложение пройдено в браузере, дополнительно написан собственный фаззинг: 4 000 случайных вызовов
`assign()` со случайными флагами подтверждения.

**Что оказалось сильным.** Доменное ядро выдержало атаку фаззингом: 723 принятых и 3 277
отклонённых назначения, ни одного нарушения вместимости, hard constraints или запрета просроченной
заявки. Разбор балла сходится с итогом до единицы. Отчёт объясняет не только результат, но и
порядок принятия решений.

**Критических дефектов (P0): 0. Сломанных путей: 0.**

### Четыре P1

1. **Принятие рекомендации записывалось как решение оператора.** Кнопка «Принять рекомендацию»
   ставила источник `manual`. Статистика «авто / вручную» искажалась, а повторное автоматическое
   распределение считало такую заявку неприкосновенной — просмотр рекомендаций по одной тихо
   отключал главную кнопку продукта.
2. **Временный дефицит мест диагностировался как «переселение невозможно».** В прогоне с урезанной
   вместимостью 7 заявок из 8 получили красный статус «переселение невозможно», хотя у шести
   единственной причиной была занятость. Оператор счёл бы заявки безнадёжными.
3. **Размещённая заявка с истёкшим сроком показывала три разные картины.** «Сводка» — 92,
   карточка — 0/100 с блокирующим конфликтом, список — бейдж места. Причина: отчёт и карточка
   считали балл разными функциями.
4. **Плитка «Без места → просрочено N» считала просроченных по всему реестру.** Число читалось как
   «из них просрочено», но включало размещённые заявки. На демо-данных ошибка маскировалась
   случайным совпадением.

### Четыре P2

Исчезающее после подтверждения сравнение с рекомендацией; четыре копии одной причины в разборе
«места нет» у просроченной заявки; очистка реестра одним кликом без подтверждения; молчаливая
перезапись нечитаемого хранилища демо-данными.

### Главное замечание к процессу

> Оценка 3/5 за управление AI. Worklog конкретен и проверяем — каждая заявленная ошибка AI
> подтверждается кодом. Но он сам себя опровергает: в разделе «Ключевые запросы» написано
> «единственный содержательный запрос, дальше автономно», при этом таблица приписывает
> разработчику восемь инженерных решений. Если человек задал одно ТЗ и одно уточнение по языку,
> эти решения принял AI.

## Ревью № 2 — вторая версия

**Итог: 4.65 / 5 · вердикт «принять»**

Изменения к первой версии: correctness 4 → 4.5, explainability 4 → 4.5, UX 4 → 4.5,
edge cases 4 → 5, AI / human control 3 → 3.5, documentation 4 → 4.5.

**Как проверялось.** Полный diff v1 → v2, фаззинг повторно — на этот раз с проверкой
согласованности сводки и карточки **на каждой из 4 000 итераций**, воспроизведение исходных
сценариев в браузере.

**Все восемь находок закрыты по существу.** Исправления сделаны в домене, а не в отображении:
`explainExistingAssignment` стал единственным источником балла и для карточки, и для отчёта,
поэтому расхождение стало невозможным структурно. Панель дефицита пошла дальше рецензии — она не
просто различает статус, а называет конкретного жильца, чьё место нужно освободить.

### Две новые P2 — обе в коде исправлений

1. **`explainNoMatch` подставлял числа одного места в причину, общую для всех.** Причины
   группировались по коду конфликта, а сообщение бралось от первого места. На живом экране:
   корневая причина «Место заполнено: занято 1 из 1» при реальной занятости других мест 2/2 и 4/4.
   Тот же класс дефекта, за который снижалась оценка первой версии.
2. **Регрессия доступности: вкладки стали недостижимы с клавиатуры.** Добавлены `role="tab"` и
   roving tabindex, но без обработчика стрелок. Неактивные вкладки исключены из обхода по Tab и
   доступны только стрелками — то есть недоступны вовсе. В первой версии, где вкладки были
   обычными кнопками, проблемы не было.

**Почему не поймано:** тест доступности проверял наличие ролей и клик мышью. Ровно тот случай, о
котором шла речь в первом ревью — важно не «есть тест», а какой риск он закрывает.

## Ревью № 3 — третья версия

**Итог: 4.88 / 5 · вердикт «принять»**

Изменения ко второй версии: correctness 4.5 → 5, explainability 4.5 → 5, AI / human control
3.5 → 4, documentation 4.5 → 5.

**Как проверялось.** Полный diff v2 → v3, фаззинг заново, клавиатура проверена **настоящими
событиями в реальном браузере** (не в jsdom), и главное — **две мутационные проверки**: ревьюер
сам ломал исправления и смотрел, падают ли написанные под них тесты.

| Мутация | Результат |
| --- | --- |
| Удалён `onKeyDown` у вкладок | Упал ровно 1 тест из 109 — новый тест на клавиатуру. Старый тест на ролях остался зелёным |
| Возвращено сравнение причин только по коду (баг v2) | Упали ровно 2 теста — оба про числа в общей причине |

**Обе P2 и четыре P3 закрыты, новых дефектов кода нет, регрессий нет.** Исправление `explainNoMatch`
сделано точнее рецензии: разделены случай «сообщения совпадают дословно» (выносится в корень) и
«код общий, данные разные» (в корень идёт формулировка без чисел, конкретика остаётся у каждого
места) — рецензия предлагала одно из двух, реализованы оба.

### Единственное оставшееся замечание — P2 к демонстрационным данным

Демо-набор не показывает два состояния, ради которых построены целые экраны: «ждёт свободного
места» (`awaiting_capacity` = 0) и «размещение требует пересмотра» (`needsReview` = 0). Оба
работают и покрыты тестами, но увидеть их можно только подменив сохранённое состояние вручную:
мест 14 на 8 заявок, дефицита штатными действиями не создать, а сдвинуть дату из интерфейса нельзя.

**Рекомендация:** добавить девятую заявку с теми же условиями, что у Сестры Вивиан (чердак + без
зеркал + без людей) — тогда одна из двух гарантированно попадёт в «ждёт свободного места»; и одну
заявку, размещённую в стартовом состоянии с уже истёкшим сроком.

не хватило бы.
