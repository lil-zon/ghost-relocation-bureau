# Бюро переселения привидений

Internal tool оператора бюро: подбирает привидениям места переселения, объясняет каждое решение,
показывает конфликты и позволяет человеку переопределить выбор системы, не нарушая правил.

Приложение полностью клиентское: ни backend, ни базы, ни внешних API. Подбор мест —
детерминированная функция, а не запрос к LLM.

---

## Overview

Оператор работает с двумя реестрами: заявки от привидений и доступные места. Система

- подбирает лучшее подходящее место для каждой заявки;
- объясняет решение фактами из расчёта, а не общими словами;
- показывает конфликты и их серьёзность;
- честно сообщает, когда переселение невозможно, и почему;
- позволяет назначить место вручную, но проверяет ручной выбор теми же правилами;
- сводит результат в итоговый отчёт.

Новый пользователь начинает работать примерно за минуту: открыть приложение → «Распределить
автоматически» → посмотреть заявки без места и разобраться с ними вручную.

## Features

- **Автоматическое распределение** с учётом приоритета заявок и изменяющейся вместимости.
- **Объяснимость**: у каждого решения есть разбор балла по компонентам и список причин.
- **Модель конфликтов** из двух уровней: блокирующие (запрещают) и предупреждения (требуют
  подтверждения).
- **Состояние «переселение невозможно»** с корневой причиной и ближайшими вариантами.
- **Ручное назначение** через ту же доменную проверку, что и автоматическое.
- **Итоговая сводка**: размещения, загрузка мест, заявки без места, частота причин отказа и
  порядок последнего автоматического прогона.
- **AI Worklog** — отдельный экран с фактическим ходом разработки.
- Сохранение состояния в localStorage и понятная обработка повреждённых данных.

## Architecture

```
src/
  domain/      чистая бизнес-логика: без React, без хранилища, детерминированная
    types.ts             доменная модель
    vocabulary.ts        человекочитаемые описания значений
    plural.ts            склонение числительных
    dates.ts             сроки; все функции принимают `now` явно
    constraints.ts       hard constraints и предупреждения
    scoring.ts           расчёт балла по компонентам
    matching.ts          кандидаты, лучший вариант, ближайшие альтернативы
    assignment.ts        валидация и применение назначения, инвариант вместимости
    priority.ts          приоритет заявки в глобальном распределении
    globalAssignment.ts  последовательное распределение всех заявок
    report.ts            расчёты итоговой сводки
  state/       состояние приложения
    store.ts             чистый reducer поверх доменных функций
    StoreProvider.tsx    провайдер + синхронизация с localStorage
    storeContext.ts      контекст и хук useStore
    persistence.ts       чтение/запись localStorage с валидацией схемы
  ui/          экраны и компоненты
  data/        демо-набор и данные worklog
```

Три правила, которым подчинена структура:

1. **Бизнес-правила не живут в JSX.** Компоненты вызывают доменные функции и отображают результат.
2. **Домен не знает про React и localStorage.** Его можно вызвать из теста, скрипта или другого UI.
3. **Время передаётся явно.** Ни одна доменная функция не читает `new Date()` внутри себя, поэтому
   поведение сроков воспроизводимо в тестах.

## Matching algorithm

Порядок принципиален: **hard constraints → scoring → выбор лучшего**.

### 1. Жёсткие ограничения

Место отбрасывается целиком, если выполнено хотя бы одно условие:

| Код | Причина |
| --- | --- |
| `location_full` | занято мест не меньше вместимости |
| `deadline_expired` | срок переселения истёк |
| `attic_required` | нужен чердак, которого нет |
| `mirrors_present` | есть зеркала при условии «не переносит зеркала» |
| `humans_present` | есть люди при условии «рядом не должно быть людей» |
| `humidity_below_minimum` | влажность ниже обязательного минимума |
| `location_closed` | место закрыто для новых жильцов |
| `anxiety_above_limit` | тревожность выше лимита места |

Главный инвариант: блокирующий конфликт → место несовместимо → автоматическое назначение
невозможно. Балл несовместимого места равен **0** и не может компенсировать конфликт.
Потенциальный балл сохраняется отдельно в `breakdown.total` — он нужен, чтобы показать оператору,
насколько близким был вариант.

### 2. Расчёт балла

Пять компонентов, каждый даёт соответствие `fit` в диапазоне 0..1:

| Компонент | Базовый вес | Как считается |
| --- | --- | --- |
| Температура | 30 | `1 − |T места − T заявки| / 12`, обрезается по нулю |
| Шум | 20 (35 при тревожности ≥ 7) | превышение над целевым уровнем, делённое на 3; цель — «тихо» при требовании тишины или высокой тревожности, иначе «умеренный шум» |
| Освещение | 15 | так же, как шум; темнее цели не штрафуется — привидениям темнота не мешает |
| Влажность | 15 | расстояние до комфортного коридора 50–85%, делённое на 30; при обязательном минимуме нижняя граница поднимается до него |
| Соседство с людьми | 10 (20 при тревожности ≥ 7) | нет людей — 1; есть люди — 0,5, а при высокой тревожности 0 |

Веса **нормализуются по их сумме**, поэтому максимум по всем компонентам всегда ровно 100, а
показанные в интерфейсе баллы компонентов в сумме дают итоговый балл без расхождений. Это важно
именно потому, что веса меняются: при высокой тревожности шум и соседство с людьми весят больше, и
с фиксированными коэффициентами шкалу пришлось бы перебалансировать вручную.

Отдельного компонента «тревожность» нет намеренно: тревожность влияет не как слагаемое, а как
изменение весов и целевых уровней — так её эффект виден там, где он реально возникает. В интерфейсе
усиленные компоненты помечены значком «вес ↑».

### 3. Выбор лучшего

Среди совместимых мест берётся максимальный балл. При равенстве — место с большим запасом
свободных мест, затем по идентификатору: результат детерминирован.

### 4. Глобальное распределение

Независимый подбор для каждой заявки привёл бы к переполнению, поэтому места занимаются
последовательно, и каждая следующая заявка видит уже изменившуюся вместимость.

Приоритет обработки:

```
priority = 0.4 × дефицитность + 0.35 × срочность + 0.25 × тревожность
```

- **дефицитность** — `100 − (число подходящих мест − 1) × 25`; единственный вариант даёт 100;
- **срочность** — `100 − дней до срока × 7`; просроченная заявка получает 100;
- **тревожность** — `уровень × 10`.

Приоритет считается один раз, на исходном состоянии: иначе порядок обработки зависел бы от уже
сделанных на этом же прогоне назначений. Цель правила — не позволить нетребовательной заявке занять
единственное подходящее место более ограниченной. Это поведение закреплено тестом.

Ручные назначения оператора при автоматическом прогоне **сохраняются**: пересчитываются только те,
что были сделаны системой.

## Conflict model

```
blocking  → назначение запрещено; домен отклоняет его независимо от состояния интерфейса
warning   → назначение допустимо после явного подтверждения оператора
```

Предупреждения: слишком шумно или светло при соответствующем требовании, соседство с людьми при
высокой тревожности, разница температур больше 6 °C, близкий срок, и отдельно —
`worse_than_recommended`, когда выбранное вручную место уступает рекомендации 15 и более баллов.

Автоматическое распределение назначает места с предупреждениями (иначе срочные заявки не
размещались бы вовсе), но сами предупреждения сохраняются и видны оператору. Подтверждение —
механизм для ручного решения человека.

Домен не полагается на заблокированную кнопку: `assign()` возвращает отказ при блокирующем
конфликте и при неподтверждённых предупреждениях, а `assertCapacityInvariant()` не даёт занятости
превысить вместимость.

## Edge cases

Проверены в тестах и вручную в собранном приложении:

- **Пустой реестр** — объяснение и кнопка загрузки демо-данных; сводка не ломается на нуле заявок.
- **Нет подходящего места** — корневая причина, список ближайших вариантов и что именно их блокирует.
- **Место заполнено** — видно в списке, в выпадающем списке ручного выбора и в сводке; домен
  отклоняет назначение независимо от интерфейса.
- **Просроченный срок** — блокирует все места; отдельно объясняется в карточке заявки.
- **Ручной конфликт** — назначение запрещено, причина и серьёзность показаны.
- **Ручное назначение с замечаниями** — двухшаговое подтверждение, результат помечен как решение
  оператора.
- **Повторный автоматический прогон** — идемпотентен и не переписывает ручные решения.
- **Повреждённое или чужое по версии хранилище** — конкретное сообщение и загрузка демо-набора
  вместо падения.
- **Ошибка рендеринга** — ErrorBoundary с текстом ошибки и возможностью очистить состояние.

## Trade-offs

1. **Жадное распределение вместо оптимального.** Венгерский алгоритм дал бы максимум суммарного
   балла, но его решение почти невозможно объяснить оператору. Порядок «сначала самые ограниченные»
   объясняется одной строкой и защищает заявку с единственным вариантом. Это осознанный отказ от
   оптимальности в пользу объяснимости.
2. **localStorage вместо backend.** Реестр в задаче живёт у одного оператора, синхронизация не
   требуется.
3. **Реестр не редактируется в интерфейсе.** Заявки и места приходят из демо-набора: формы
   создания не добавляют ничего к проверке основного сценария.
4. **Место занимается бессрочно.** Учёт занятости во времени — отдельная и заметно более сложная
   модель, которой задача не требует.
5. **Тесты сосредоточены на домене.** Интерфейс покрыт сценарными проверками ключевых путей, а не
   попиксельно: инварианты живут в домене, и проверять их там дешевле и надёжнее.

## Future improvements

1. Оптимальное распределение вторым режимом — с показом разницы в суммарном балле, чтобы была
   видна цена объяснимости.
2. История решений с откатом: сейчас предыдущее состояние теряется после автоматического прогона.
3. Редактирование заявок и мест прямо в интерфейсе.
4. Настраиваемые веса scoring — правила у разных отделений бюро могут отличаться.
5. Занятость во времени: место могло бы освобождаться по окончании срока переселения.
